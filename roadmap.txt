DECISÕES TÉCNICAS REGISTRADAS
==========================
(cada entrada: data — decisão — por quê)

- 2026-07-06 — SQLite escolhido em vez de Postgres na Fase 1 — zero setup
  necessário para começar a desenvolver localmente; migração para Postgres
  planejada antes do deploy (Fase 6).

- 2026-07-06 — Gerenciamento de dependências Python via venv + requirements.txt,
  não Poetry — simplicidade para um projeto de portfólio.

- 2026-07-06 — Parsing de CSV usa correspondência de colunas genérica
  (lista de nomes candidatos + fallback de formato numérico/data brasileiro)
  em vez de schema fixo da XP — nenhuma exportação real estava disponível
  no momento do scaffold. Precisa ser ajustado quando um export real
  chegar em data/raw/.

- 2026-07-06 — Parser de CSV agora detecta automaticamente o delimitador
  (vírgula ou ponto-e-vírgula) em vez de assumir vírgula fixa — um teste
  real (tests/test_ingest.py) revelou que valores no formato brasileiro
  ("-1.234,56") quebram um parser delimitado por vírgula, já que a vírgula
  decimal colide com o delimitador. Exports brasileiros comumente usam
  ponto-e-vírgula por esse motivo exato.

- 2026-07-06 — Duplicatas são permitidas no re-upload de CSV por enquanto
  (sem lógica de dedup) — decisão de adiar até entender o que é uma
  duplicata real num export da XP.

- 2026-07-06 — Transaction.category é nullable na ingestão — categorização
  (baseada em regras, depois ML) é a Fase 3, não faz parte da ingestão.

- 2026-07-06 — Versões fixadas em requirements.txt foram atualizadas
  (fastapi 0.115.6, pydantic 2.10.4, sqlalchemy 2.0.36, python-multipart
  0.0.20) — pydantic-core==2.7.4 não tem wheel pré-compilada para Python
  3.13 nesta máquina, forçando build via Rust/cargo que falhava no linker
  do MSVC. Isso tinha sido erroneamente diagnosticado antes como bloqueio
  do proxy SSL corporativo; não era — pytest (pacote pure-Python) instalou
  normalmente, isolando o problema ao build nativo do pydantic-core.

- 2026-07-06 — Adicionados pytest e httpx como dependências de
  desenvolvimento para permitir testes automatizados (item "Testes básicos
  do parsing de CSV" da Fase 1). Testes de API usam SQLite in-memory com
  StaticPool para isolar cada teste do banco de desenvolvimento real.

- 2026-07-06 — Criado backend/tests/fixtures/sample_statement.csv (dados
  sintéticos, não reais) no formato ponto-e-vírgula/brasileiro plausível
  de um extrato da XP. Objetivo duplo: (1) teste de integração cobrindo
  parser + endpoint juntos com um arquivo real em disco, e (2) permitir
  testar o app manualmente pelo navegador (upload via file picker) antes
  de haver um export real da XP disponível.

- 2026-07-06 — Sistema visual final importado do projeto Claude Design do
  usuário ("Finance Dashboard System.dc.html", via DesignSync MCP) e
  implementado em frontend/src/: theme.css com os tokens (navy dominante
  #12202E, accent copper #C9752F, fontes Space Grotesk/IBM Plex Sans/
  Archivo), componentes TopNav/SummaryCard/TransactionsCard, e
  utils/summary.js. Manteve o nome "Finance Tracker" na navbar em vez de
  "Ledger" (nome usado no mockup do design) — decisão do usuário para não
  criar divergência de marca com o resto do projeto (README, docs).

- 2026-07-06 — Cartão de resumo (saldo/receita/gasto) calculado no
  frontend a partir de GET /transactions, sem endpoint novo no backend —
  soma simples de amount (saldo), soma dos positivos (receita) e soma dos
  negativos (gasto). Formatação de moeda em BRL/pt-BR (Intl.NumberFormat),
  não USD como no mockup, já que os dados reais serão de uma corretora
  brasileira (XP).

- 2026-07-06 — Indicador de variação "vs. mês anterior" só aparece quando
  há pelo menos 2 meses distintos nos dados (compara saldo acumulado até
  o fim de cada mês); com menos de 2 meses o indicador fica oculto em vez
  de mostrar uma tendência inventada — consistente com o princípio 04 do
  próprio sistema de design ("Honest states").

- 2026-07-06 — Dinheiro migrado de Float para Decimal via TypeDecorator
  (centavos inteiros no SQLite, Decimal no Python, string decimal exata no
  JSON) — floats binários acumulam erro de arredondamento em agregações;
  é o erro clássico de domínio em finanças. Centavos inteiros mantêm SUM
  exato no SQLite e portam sem mudança para Postgres. O frontend usa
  Number() só para exibição, nunca para contabilidade.

- 2026-07-06 — Categorização por regras com rastreio de origem
  (category_source='rule'|'user') — correções manuais nunca são
  sobrescritas pelo reprocessamento e formam o dataset rotulado para o
  categorizador ML da Fase 3. Regras com primeiro-acerto-vence, ordenadas
  da categoria mais específica para a mais genérica.

- 2026-07-06 — Agregações (summary/monthly/by-category) movidas para SQL
  no backend em vez de JavaScript no frontend — é a habilidade que o
  portfólio quer demonstrar, e sum/coalesce herdam o tipo MoneyCents do
  SQLAlchemy, então nenhum float entra na agregação. strftime('%Y-%m') é
  específico do SQLite; trocar por to_char/date_trunc na migração Postgres.

- 2026-07-06 — Proxy do Vite (/api → localhost:8000) em vez de URL
  hardcoded + CORS por regex — requisições same-origin em dev; porta do
  Vite fixada em 5178 para o run.ps1 achar o app (com varredura de portas
  e checagem do <title>, já que o log do Vite tem códigos ANSI que
  quebravam o parsing por regex).

- 2026-07-08 — Usuário adicionou os 2 tipos reais de arquivo em data/raw/:
  extrato bancário (extrato_de_*.csv) e fatura de cartão de crédito
  (Fatura*.csv). Descoberto por inspeção: extrato usa ano com 2 dígitos
  ("06/07/26") e "-R$ X,XX" (sinal antes de "R$"); fatura usa ano com 4
  dígitos e "R$ -X,XX" (sinal depois de "R$"). _parse_amount corrigido
  para remover todo espaço em branco após tirar "R$", não só as pontas —
  "- R$ 2.400,00" virava "- 2.400,00" (espaço interno) e quebrava o
  Decimal(). DATE_FORMATS ganhou "%d/%m/%y".

- 2026-07-08 — DECISÃO (confirmada com o usuário): fatura de cartão tem
  convenção de sinal invertida (compra = positivo no arquivo) e a linha

  bancário como "PAGAMENTO DE FATURA" (confirmado batendo os valores nos

  "Pagamento de fatura" são descartadas ao processar fatura de cartão

  invertido para ficar negativo (convenção do sistema: negativo = gasto).
  Sem essa correção, /analytics/summary contaria o pagamento da fatura
  duas vezes.

- 2026-07-08 — Coluna "Parcela" (parcelamento) da fatura é anexada à

- 2026-07-08 — DECISÃO (confirmada com o usuário): "Credit Card Payment"

- 2026-07-08 — RESOLVIDO: bug real de SQL encontrado testando essa

- 2026-07-06 — RESOLVIDO (2026-07-10, ver desfecho ao final da entrada):
  no teste do run.ps1, o backend não respondeu em /health dentro dos 30s
  de polling (o frontend subiu e o navegador abriu normalmente).

  Investigação de 2026-07-10 — o que foi encontrado:

  1. ACHADO (resolvido): um worker uvicorn --reload órfão, de uma sessão de
     2026-07-06, estava vivo havia 4 dias e ocupando a porta 8000 sozinho,
     respondendo /health normalmente. `uvicorn --reload` no Windows spawna
     o worker real via multiprocessing.spawn; esse worker sobrevive ao
     fechamento da janela/console que o originou (matar a janela PowerShell
     pai — mesmo com Stop-Process -Force — não mata o worker). Levou 3
     tentativas de kill para identificar e encerrar o processo certo: o PID
     reportado por Get-NetTCPConnection ficava "piscando" entre existir e
     não existir por causa do próprio ciclo de restart do --reload. Processo
     órfão finalmente encerrado; porta 8000 confirmada livre.
     CORRIGIDO em run.ps1: antes de abrir uma janela nova, verifica se
     algo já responde em /health na porta 8000 e reaproveita em vez de
     duplicar (evita a colisão silenciosa que esse tipo de órfão causa).
     Mensagem de erro inclui o comando para o usuário encerrar manualmente
     um processo antigo caso o reaproveitamento não seja o desejado.

  2. ACHADO (mitigado, não eliminado): por padrão, `uvicorn --reload`
     escaneia recursivamente todo o diretório de trabalho (backend/,
     incluindo venv/ — dezenas de milhares de arquivos) para montar seu
     estado inicial de observação de arquivos, antes de considerar o
     servidor "iniciado". Nesta pasta sincronizada via OneDrive, cada
     stat() desse escaneamento passa pelo filtro de sincronização em
     nuvem. Medido: um teste ficou mais de 45s sem responder /health com
     esse comportamento padrão.
     CORRIGIDO (parcialmente) em run.ps1: adicionado `--reload-dir app`
     ao comando do uvicorn, restringindo o watcher a backend/app/ (poucos
     arquivos .py) em vez do diretório inteiro. Testado isoladamente
     (uvicorn lançado direto, sem janela nova): respondeu em bem menos de
     1s, contra >45s antes da mudança.

  3. NÃO RESOLVIDO: mesmo com a correção 2 aplicada, rodar run.ps1 de
     ponta a ponta (via Start-Process, do jeito que o script realmente
     lança o backend, em janela PowerShell nova) ainda produziu "Backend
     didn't answer within 30s" nesse timeout — porém um monitor externo
     confirmou que o backend ficou saudável pouco depois, já fora da
     janela de 30s do script. Ou seja: o fix da causa 2 reduziu bastante o
     tempo de start "puro" do uvicorn, mas o caminho específico de lançar
     via Start-Process em janela nova ainda carrega uma sobrecarga extra
     não isolada — hipóteses não testadas: escaneamento de antivírus/EDR
     corporativo num processo/janela recém-criado, custo de inicialização
     do console/conhost do Windows, ou alguma interação adicional com o
     OneDrive específica de janelas novas. Uma medição controlada e
     cronometrada do caminho exato do Start-Process foi iniciada para
     isolar a causa, mas foi interrompida antes de terminar.

  ESTADO em 2026-07-10 (parcial): run.ps1 tem as correções 1 e 2 aplicadas
  (reaproveitar backend já rodando + `--reload-dir app`), timeout em 30s.
  Restava a causa 3 não isolada.

  RESOLVIDO (2026-07-10, mais tarde na mesma sessão) — causa 3 isolada e
  corrigida. Não havia NENHUMA sobrecarga no Start-Process: medição
  definitiva com 3 sinais em paralelo mostrou o backend escutando na porta
  e respondendo 200 via curl em ~0s após o Start-Process. O que falhava
  era o PRÓPRIO POLLING do run.ps1:

  CAUSA REAL: Invoke-WebRequest (PowerShell 5.1 / .NET Framework)
  "envenena" o processo quando a primeira sondagem acontece antes do
  servidor abrir a porta. Nesta máquina, o connect a uma porta local
  fechada não é recusado (RST) — o SYN é descartado (provável firewall/
  EDR), então a tentativa trava até o TimeoutSec. As tentativas abortadas
  ficam presas no ServicePoint do .NET para aquele host:porta (limite
  padrão de 2 conexões), e TODA chamada IWR subsequente à mesma URL no
  mesmo processo entra na fila atrás delas e expira para sempre — mesmo
  com o servidor já de pé. Comprovado: poller IWR falhou por 240s
  seguidos com "O tempo limite da operação foi atingido" enquanto curl
  respondia 200 na mesma URL o tempo todo, e um IWR novo em OUTRO
  processo respondia 200 na hora. Como o run.ps1 sonda /health
  imediatamente após o Start-Process (antes do uvicorn abrir a porta), a
  falha era determinística. Também explica por que o check do frontend
  nunca falhava: a primeira sondagem ao Vite acontecia depois do Vite já
  estar de pé (nunca envenenava).

  FIX: função Test-Health em run.ps1 usando curl.exe (embutido no
  Windows 10+) no lugar de TODOS os Invoke-WebRequest do script (check
  de reuso, polling do backend e varredura de portas do frontend).
  Detalhe importante: o sufixo .exe é obrigatório — "curl" sem sufixo no
  PowerShell 5.1 é alias de Invoke-WebRequest.

  VERIFICADO de ponta a ponta: com nenhum processo nas portas (estado
  frio real), `powershell -NoProfile -File run.ps1` subiu backend +
  frontend e abriu o navegador em 5 segundos, sem nenhuma mensagem de
  aviso. O item está encerrado.

  ACHADOS COLATERAIS da mesma investigação (registrados para o futuro):
  (a) Os testes e2e anteriores deixaram 3 workers uvicorn órfãos
      (multiprocessing-fork), cada um segurando o socket herdado da porta
      8000 mesmo com o pai morto — o netstat continua mostrando o PID do
      processo que fez o bind (já morto), então `taskkill /T` no PID da
      janela não os alcança (a árvore quebra quando o pai morre). Para
      matar de verdade: procurar processos python com
      "--multiprocessing-fork" na linha de comando e matar pelo PID deles.
  (b) Erro de diagnóstico meu durante a sessão: usei
      `grep "LISTENING.*:8000"` para conferir porta livre, mas o netstat
      imprime o endereço ANTES da palavra LISTENING — o padrão nunca
      casava e deu "porta livre" falso várias vezes. O padrão correto é
      `grep ":8000" | grep LISTENING`. Registrado porque contaminou parte
      das medições intermediárias (não as conclusões finais, refeitas com
      o check correto).
  (c) O Vite escuta em [::1] (IPv6), não em 127.0.0.1 — qualquer
      diagnóstico futuro de porta do frontend precisa olhar IPv6 também.
